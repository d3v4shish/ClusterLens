# Architecture

ClusterLens is a local PyQt desktop application. `apps.pyqt_production` builds the shell, owns QSettings/runtime services, and exposes four workspaces: Library, Organize, People, and Tools. A contextual `QTabBar` selects sections within the active workspace; legacy Gallery, Clustering, Faces, Names, and Tags route IDs migrate to the closest new surface. Mature pane implementations remain internal so this information-architecture change does not duplicate storage or workers. Organize Basic owns the sectioned active-root photo grid; Advanced reveals clustering controls/comparison. People lazily creates face/name services on workers and never indexes merely because the workspace opened. Tools routes duplicate review, batch rename/metadata, and recovery through existing safe services.

People persists only a versioned lightweight QSettings payload: stable route/filter IDs, splitter sizes, disclosure choices, and the explicit walkthrough-dismissed bit. It never stores result paths, jobs, or model output. The one supported unversioned predecessor is migrated once from `workspace/people_state` to `workspace/people_state_v1`; unknown or malformed versions fail closed to defaults. Restore happens when the lazy pane is created and is independent of whether a previously selected root still exists, so it cannot scan media or replay an action during startup.

The shared **Roots** drawer is the single persisted `PathScope` editor for all workspaces. `SourcePane` owns a draft `PathScope` while its Sources tab is open; a checked filesystem row changes that draft only, while `apply_draft()` alone emits `scope_changed` and lets the shell update settings or start scope-dependent work. `discard_draft()` restores the committed scope, and the shell handles a dirty close with Apply/Discard/Continue editing. The separate Catalog tab unifies active and registered roots for registration, enable/disable, refresh, pause, reveal, and derived-record removal; catalog mutations are disabled for a dirty draft or read-only safety mode. It intentionally separates managed **Data Home**, which owns indexes, previews, models, operation journals, backups, logs, and reports. The header retains a compact scope chip, Jobs, and Settings; verbose job state collapses at compact breakpoints but cancellation and the full tray remain reachable. Reusable `EntityPicker` controls receive choices from background services and provide consistent click/Enter/Tab completion. The shared Photo Inspector keeps the image dominant and uses Info, People, Metadata, and EXIF panels. Metadata and face drafts independently require Save/Discard/Cancel before navigation or close.

`ui.theme.ThemeManager` owns the process-wide semantic palette and resolves the persisted `system`, `light`, or `dark` preference plus an independent 100/125/150/200% text scale. Qt's color-scheme signal can re-resolve only the system preference; palette, stylesheet, auto-colored SVG icons, revision-aware custom delegates, hover previews, viewer chrome, and runtime badges update together on the UI thread. Text-scale changes schedule one shell reflow: content hints are invalidated, the user-selected People splitter width remains the baseline, the task rail grows only when live font metrics require it, and the active route/focus/input state is retained. At the 1280×720 contract, header/runtime copy compacts and secondary Roots, Settings, People, and Advanced Organize surfaces wrap or scroll vertically; they never require horizontal panning. Readable semantic foreground/background pairs target 4.5:1 contrast and focus/indicator boundaries target 3:1. Jobs attach the exact queued/running/cancelling/done/cancelled/failed semantic state to progress controls, while status text and accessibility descriptions keep the outcome understandable without color. The shared stylesheet uses matte semantic surfaces plus explicit numeric, short, and medium field-width hints. The photo inspector deliberately has a separate canvas preference. Its existing preview worker downsamples the already-decoded `QImage` to 32×32, samples the outer border while ignoring mostly transparent pixels, and returns one neutral backdrop with the preview. No source I/O, metadata query, GPU task, or app-chrome color derives from the photo. Existing QSettings profiles migrate to dark/theme-canvas/100% compatibility; fresh profiles use system/adaptive-neutral/100% defaults.

`KeyboardTabBar` keeps arrow navigation inside workspace/People route selectors but explicitly advances Tab and Shift+Tab through the surrounding focus chain. Modal Settings/runtime/source flows and the modeless Jobs monitor restore focus to their invoker, or to a visible fallback when the invoker was removed. Hidden disclosure bodies remain outside traversal. Composite fields retain label buddies, and People/Jobs status, progress and cancellation controls expose meaningful names and descriptions without relying on color.

UI release evidence is generated from isolated runtime/settings directories and a small generated active photo root. The offscreen verifier walks the declared route, Settings, Inspector, Roots and Jobs state matrices, while the native verifier repeats route/Settings geometry and logical keyboard coverage on a real Qt platform. Its optional multi-screen gate assigns the real window surface to each Qt screen that can contain the requested supported client size and verifies the compositor-reported target, containment and app-only capture; it does not lower the product minimum merely to fit a narrow output. Both verifiers fail closed on missing states, first-run masking, clipping, unnamed or unreachable controls, contrast failure, background work that does not settle, or incomplete shutdown. Native screen-reader behavior remains a separate assistive-technology boundary and is never inferred from Qt focus, AT-SPI event presence or accessible-name checks. Canonical tests inherit a Python-level external-network guard and offline model flags; the Linux release audit separately follows every native descendant's network syscalls and rejects non-loopback or unparseable IP destinations. That audit is evidence, not an application runtime sandbox, so production remote providers remain governed by their explicit user-consent boundary.

`DataHomeManager` is the single ownership boundary for managed-data inventory,
checksummed backup verification, and relocation. A backup is built under an
app-marked hidden sibling staging name and becomes visible only through atomic
directory publication after its manifest is durable. A source-side backup
journal makes copying/verified/published interruptions discoverable in Storage;
discard validates the exact journal and marker before removing only staging,
while an already published backup is checksum-verified, retained, and finalized.
Relocation copies only known managed
categories into a sibling staging directory, verifies a manifest, atomically
switches the directory, and writes the next-launch pointer only after
verification. Resuming a verified staging copy re-verifies that immutable
manifest and never recopies a changed source; an incomplete copy requires the
active Data Home to remain available. Its source-side journal supports preview,
resume, and discard of an incomplete staging area; no photo root is eligible as
a target.
Storage starts these actions in `AsyncJob` workers, exposes them in Jobs, and
includes them in dialog cancellation/shutdown. `JobManager` distinguishes
queued, running, cancelling, and terminal work; Jobs snapshots update only
changed rows, and Esc cancels the most recent cancellable foreground job before
falling back to clustering cancellation. Foreground footer ownership is stable:
the newest registered foreground job owns status/progress until it terminates,
independent of which concurrent worker emits progress most often. An older job
then resumes if still active; background and stale terminal updates remain in
Jobs. While progress is owned, unrelated direct footer copy is deferred rather
than replacing the visible phase. `WorkCoordinator` is the
resource declaration layer for newly migrated independent Jobs: it permits
unrelated work, serializes declared Data Home/source/GPU conflicts, propagates
failed dependencies, and offers Queue, CPU fallback, or Cancel for CUDA
contention according to the persisted policy. Its AsyncJob adapter delays
thread creation until ownership, binds progress and terminal state to the same
Jobs row, and reports pre-start cancellation or rejection without dispatch.
The deterministic conflict verifier exercises this production object directly
and records its signal journal for both launch orders across GPU, Data Home,
model-cache, overlapping-source, and compatible read-only pairs. It checks
queued/running cancellation, failure/retry, and an empty final ownership set;
native/UI workload responsiveness remains a separate qualification boundary.
Library catalog/Timeline, duplicate review/Trash, People Cleanup, cluster
context, and Tags now submit through that adapter with their actual workspace
owner and Data Home/source read-write declarations. Remaining legacy job entry
points are tracked explicitly in `TODO.md` until migrated.

Library owns a managed runtime SQLite catalog (`cache/library_catalog.sqlite3`) for explicit registered roots. A background scan first applies the same immutable `SourceAdmissionPolicy` snapshot used by production Gallery, Clustering, Faces, and similarity discovery; only then does it read admitted paths' scalar EXIF and embedded/XMP/ClusterLens sidecars and maintain ordinary SQLite indexes plus FTS5 when available. Asset and FTS rows commit together in bounded transactions. Each commit publishes its exact root-local subset to Library; cancellation reloads those durable rows and counts, while a fully returned scan is not reclassified by a late Cancel click. The policy can exclude conventional thumbnail names, a minimum width/height, and a minimum byte size. Disabled rules are a stat/name fast path; enabled dimensions open only image headers in the existing cancellable worker. Settings changes create a new snapshot for new work; a Library refresh reconciles its derived rows against that snapshot. The catalog never writes source media. A valid capture time saved in a reversible `<photo>.clusterlens.json` sidecar is explicit user intent and wins over the chosen source policy. Otherwise, that policy orders EXIF, a filename time, and modification time. Filename recognition receives persisted ordered safe legacy `strptime` formats plus a fixed named-token grammar: `{date:YYYYMMDD|DDMMYYYY|YYYY-MM-DD|DD-MM-YYYY}`, optional `{sequence:N}`, and declared `{epoch:s|ms}`. A scan compiles rules once, stores a same-day `capture_sequence` separately from `captured_at`, and can opt into a bounded raw-ID epoch fallback only when exactly one 10- or 13-digit candidate is valid from 1991 through the current UTC year. Every Timeline candidate is bounded to that year range; `filename_only` falls back to valid camera `DateTimeOriginal` before it leaves a missing/invalid filename value unparsed, never to modification time. Invalid, empty, and stale database values are grouped in a virtual explicit Unparsed row. It never executes user regular expressions, infers a date from a counter, or accepts ambiguous raw candidates. Timeline exposes the rules and fallback setting beside a cancellable forced derived-data refresh; recomputation changes catalog rows only. Its filter form uses a coalesced UI-only reflow: each primary cell's live size hint plus current scroll-viewport width selects one row, the semantic two-row fallback, or a narrow stack; the advanced body uses the same measured rule and the tab height follows the form up to a compact scroll cap. Resize, font, style, and layout-direction changes never touch catalog/media work. Timeline then performs a cancellable full filtered SQLite read of `image_path` and `captured_at`, ordered by `capture_sequence`, retaining scalar day/ISO-week buckets for a persisted Year, Year → Month, Year → Month → Week, or Year → Month → Day virtual `SectionedGallery` hierarchy. Changing the grouping republishes that in-memory result; it does not reread the catalog or source media. Only the newest selected leaf starts expanded and thumbnail work remains viewport-bound. Search and saved-album browsing remain 500-photo paged `GalleryPane` views. Its People Cleanup service lazily opens the existing durable face index only for catalogued, enabled-root paths; its duplicate service combines exact SHA-256 groups, pHash candidates, optional existing visual vectors, and capture-time bursts into review-only groups. Duplicate review reads only its in-scope persisted vectors in bounded SQLite batches, not the complete global index. Gallery file actions use one append-only SQLite journal for copy/move/Trash/rename; every file intent is durable before mutation, in-place renames are previewed as an all-or-nothing collision check, and moves can use the restore path. Startup reconciles interrupted intents from the original/target file manifest without moving or deleting ambiguous duplicates; recovered move/Trash/rename rows remain explicitly restorable and repeat recovery is idempotent. Settings reports the catalog as a separate generated-storage category; clearing it is a background operation that removes derived asset/context rows while retaining registered roots, albums, and curation feedback.

Library Search's disclosed capture-range, camera, folder, and extension fields map directly to the existing local `CatalogQuery` and do not start media work. A selected duplicate group hands its members to the existing full-size main-gallery route for inspection. The pHash candidate lookup uses radius-plus-one non-overlapping blocks, preserving Hamming-radius candidates whose bit changes span old 16-bit bands; it may still enumerate a large same-block bucket before precise filtering.

`ClusterContextService` selects one deterministic representative per cluster (catalogued capture time, then path), resizes it in a worker, and sends it with scalar EXIF/XMP only to a selected local Ollama or explicitly consented OpenAI-compatible provider. Generated title/description/keywords and cluster membership stay in the Library catalog for FTS-backed, cluster-first text search. Automatic generation is a sequential, opt-in Library Job after clustering; it is disabled by default and does not run a remote provider without fresh per-run consent.

`SourcePane` owns one persisted canonical, non-overlapping active-root `PathScope`, plus a temporary draft while Roots is being edited. Browse location and source scope are separate. A tree checkbox changes only that draft; a tree-row click only navigates. `PathScope` collapses nested roots and `roots_scope_sql` applies exact-or-descendant predicates; an empty committed scope matches nothing. Root-union discovery starts only after the shell receives the committed `scope_changed` signal, stays cancellable in workers, and de-duplicates paths before consumers receive a snapshot. Library registration stays explicit. Cross-workspace selections use an in-memory `PhotoSetRoute`; changing the route never starts detection, indexing, clustering, or source mutation implicitly.

Tags is a database-backed hub over `ImageTagService`'s `image_tags` SQLite table. Its `(tag_norm, image_path)` index supports deterministic pages of global/current-folder tag inventory and selected-tag photo paths without reading EXIF or source files. Gallery retains per-photo tag editing, including optional EXIF mirroring. Tags-only global rename/merge and delete change database rows only, by design. The Tags filter is the sole production source for tag-filtered cluster requests. Selected-cluster meaning generation is on demand: an `AsyncJob` creates local, no-download embedding/meaning services off the Qt thread, publishes only if the exact selected cluster remains current, and exposes cancellation/progress through `JobManager`; applying its labels is another background database-only mutation.

Clustering workers discover images, generate embeddings, cache results under the application runtime, and return compact result data to the UI thread. Gallery widgets use paged/model-backed presentation and bounded thumbnail caches. `GalleryPane` prioritizes exact visible tiles from the viewport centre, then directional prefetch; changing the viewport invalidates queued obsolete indices. `SectionedGallery` advances a viewport epoch, clears not-yet-started stale runnables, and schedules visible tiles ahead of header previews. For a 2,000+-path section hierarchy, it first creates immutable normalized rows/path locations in an owned cancellable worker, then commits one current-generation snapshot on the UI thread; initial section publication, explicit Timeline collapse state, and resize column reflow share that path and restore stable selection/scroll identity. In-flight image reads are not interrupted but generation guards prevent them from painting stale views. The thumbnail cache owns a SQLite access index beside its WebP files; opening it reconciles completed cache files, removes stale/unsafe rows, and recreates a corrupt index without touching source media. Multiple thumbnail services share a bounded process-local completed-recovery state only while the cache's WebP/index fingerprint matches, avoiding repeated recovery scans without persisting new state or bypassing recovery after a change.

Faces has two storage boundaries: per-folder review/index data and a global face database mapping face records to image paths. Faces uses the shared active-root scope by default, with an exact session route taking precedence only while Folder Review is active; Find can never accidentally inherit that review database. Entering People loads only the active surface; inactive All Faces/Folder Review data is marked stale and loaded when opened, without indexing or rescanning. The primary People selector exposes **People**, **All Faces**, **Unnamed**, **Detect**, **Review**, **Review & Name**, **Find**, and **Manage**. Stable route IDs synchronize the shell, task selector, album filter and Folder Review subtabs in both directions; a bounded legacy alias table migrates old names, while unknown routes are rejected rather than falling through to All Faces. Review is the pending-proposal people-cleanup surface; Detect and Review & Name route to the two explicit sub-surfaces of Folder Review; Manage routes to the persisted identity browser and maintenance controls. Photo-review context handoff sets an explicit Detect scope but never calls detection. Find uses a compact Photo/Saved person selector and renders only the chosen primary workflow above selection and administration. Its photo path actions wrap at narrow/large-text widths, a sole detected face is selected without an unnecessary chooser, and the owned viewport timer keeps the task, query and current action together without discarding either query. Its visible Workflow card contains the optional walkthrough and saved-search controls. Detailed guidance is available through hover and `i` help controls. Its **Search all indexed faces** Power-user option explicitly removes the active-root and selected-photo working-set restriction for that request. Identity maintenance and danger-zone groups remain collapsed by default and preserve read-only plus confirmation safeguards. The active detector/embedder pipeline and review filters are selected in a modal editor.

Removing a face database checkpoints SQLite, releases retained face/ANN caches, and atomically stages only the database, WAL, SHM and matching ANN sidecars below `cache/.face_storage_recovery/<operation>/`. A versioned journal is the commit boundary: cancellation or restart before commit restores the old store, while a committed removal remains recoverable until a separate explicit restore or discard. Startup recovery is idempotent, rejects unscoped journal paths, and never targets source photos or external model directories. People invalidates every published face/identity/count snapshot after a committed removal; the shared coordinator excludes concurrent Data Home readers and writers.

`FaceIndexService.prepare_folder_review_candidate_snapshot` creates one cancellable, symlink-safe, scoped canonical path map for a Detect review generation. `load_folder_review_image_page` accepts that private snapshot and returns at most 500 source-ordered images plus total/next-offset metadata; nested review and scan-state reads reuse the page's checked keys, while database rows retain canonical scope checks. Its face-index and scan-state queries are limited to that page. `SearchPane` prepares the snapshot in its worker before publishing the first page, then a generation-guarded worker reads every remaining page as immutable metadata snapshots. A durable indexing batch invalidates the prior snapshot before the replacement cache worker starts. Cache completion merges review metadata but does not touch the visible Photos gallery or build Faces tiles. Only a visible Photos-tail request appends one prepared page with path-limited model updates, preserving scroll, selection, thumbnail cache, and loaded rows; a tail request received during cache fill is remembered. A folder/scope/filter/sort/mode/tab change cancels obsolete work. All Faces uses the existing member-page interface with a 500-member limit and automatically continues only the selected group; selecting another group cancels the prior stream. Both surfaces use model-backed grids rather than one widget per face.

Face indexing is a bounded background pipeline. Active-root discovery produces a de-duplicated path snapshot; unchanged scan rows are skipped before image work. Up to eight CPU decode futures feed one detector lane because the supported SCRFD model has a batch-one input. Crop-quality scoring runs in a bounded CPU pool while the dynamic ArcFace embedding lane consumes cross-photo crop batches; a single SQLite writer commits bounded groups of image records and invalidates identity/ANN caches once per durable group. Cancellation is observed before that commit point; once committed, the bounded name-import/cache bookkeeping finishes and the returned metrics survive a late cancellation request. After each successful commit, `index_paths` emits only the committed image paths to its optional observer. Detect queues those paths into its active review source and restarts only an unpublished review-metadata cache when new durable rows arrive; it never refreshes the visible Photos viewport or builds a hidden Faces model. The service reports both retained ONNX providers and every worker/batch limit in job metrics. The normal action preserves unchanged rows; the visible Reindex action passes `force=True`, never edits source media, and retains compatible durable labels during record replacement. CPU execution is selected only by the verified runtime policy when CUDA ONNX is not available.

All Faces uses model-backed group lists: Named Photos merges face tiles by their persisted person name, while Grouped Photos displays the raw clustering groups. Its All Faces sidebar exposes an All/Labelled/Unlabelled selector; this becomes a `group_kind` constraint in the paged SQLite album query before counts and offsets are computed. Labelled is a durable saved name, Unlabelled is a durable unnamed face, and pending proposals are **Review-only** so one face never appears under conflicting states. The first group and its first bounded member page share one SQLite read snapshot; later member pages are requested only for the selected group. Its sidebar maintains status internally for result publishing but renders only paged actions with hover and help affordances. The shared dense theme differentiates navigation tabs, subordinate result tabs, fieldset sections, primary actions, and secondary/configuration actions through explicit QSS selectors and `kind` properties. Its geometry-static application stylesheet resolves semantic colors through dedicated `QPalette` roles, so dark/light changes update the palette, icons and custom painters without global stylesheet repolish; density and text-scale changes still rebuild QSS because they intentionally change geometry. Face Groups keeps naming and photo viewing visible, moves less-frequent review/inspection work into Actions, and exposes cluster editing only through Advanced Actions. Manage places the normal identity list and prototype actions before explicit Management and Danger-zone expanders. Their bodies are genuinely hidden when collapsed, persisted as lightweight UI state, and refresh the same selection, busy, and read-only predicates when opened; destructive buttons are non-default and still require their action-specific confirmation. Background result filtering resolves saved metadata for every tile, so raw cluster titles list every current name in the cluster and naming in Detect, selected Grouped Photos tiles, grouped clusters, or another workspace is reflected in all views after the global album, folder review, identities, result groups, and Names refresh. Detected-face and Grouped Photos tiles use standard extended selection: Shift selects a range, Ctrl changes individual membership, and a right-click on an already selected tile preserves that selection. Raw cluster groups also support extended selection for batch naming. Single-face menus contain only single-face actions, while multi-face menus contain only batch-safe naming, clustering, and removal actions. Menus are shown asynchronously, so opening one does not nest a UI event loop. Menu, toolbar, saved-search and direct-handler entry points share the same scope, readiness, selection, read-only and local-busy predicate; queued work counts as busy even before thread creation, and handlers re-read selections to reject stale rows. The predicate does not blanket-disable independent saved-search edits or clustering-filter handoffs, while the coordinator queues actual resource conflicts. Find by Face embeds a supplied query photo; Find by Name + Similar uses the saved identity prototype embedding and therefore returns named and still-unlabeled similar faces. Detect also supports an explicit ignored-only recovery view: a per-face durable ignore flag excludes that region from ordinary Faces, Names, search, and clustering queries until Restore returns it. Name entry fields and prompts load durable non-hidden names asynchronously for completion while accepting new names.

Face labels are durable `(image_path, face_index) → person_name` rows in the global face SQLite database. Explicit user naming first merges the exact normalized face rectangles into MWG/XMP `mwg-rs:Regions`; a successful photo or sidecar write is required before its SQLite row is committed. JPEG embeds XMP and carries a ClusterLens EXIF UserComment mirror; non-JPEG formats and pre-existing XMP sidecars use `<photo>.xmp`. The XMP region list and custom mirror preserve unrelated metadata and every other face region. An explicitly selected saved region bypasses the automatic prototype-quality gate for name, rename, and unlabel mutations, so the metadata write and durable label cannot diverge; automatic proposals, matching, search, and clustering retain their configured quality filters. Re-index imports only an external region that matches an otherwise-unlabeled face; an existing database label wins on conflict. Automatic suggestions remain in `pending_face_labels` until review. A background global-album/Names refresh performs a one-time legacy recovery for earlier `manual_selected_faces` proposals; it promotes unconflicted rows, removes redundant duplicates, and leaves conflicts pending rather than replacing a durable assignment. The Names workspace reads `face_labels`, uses a paged name list, and queries distinct image paths for the selected name on a worker thread. Its default gallery remains a photo view of exact face mappings. Its explicit **Find Similar Faces** action performs the saved identity-prototype search and bounded background face-crop decoding, then shows individual face tiles with score, durable-name state, bbox, and photo-opening context; selection changes cancel or discard stale publications. Hovering a name runs a separate cancellable worker query and builds at most a nine-photo contact sheet; a 24-entry in-memory LRU cache prevents repeated thumbnail work and stale results are discarded by generation. Its workspace-specific Rename and Unlabel actions first present the actual region names found in selected files, then mutate only the matching regions. Identity duplicate/prototype reads, mutation writes, and pre-confirmation counts all run in coordinated workers; cancellation before confirmation cannot mutate the database. Saved People searches use atomic JSON replacement plus a per-path edit lock and an independent background UI lifecycle, so slow or malformed storage cannot freeze or overwrite the current view. Faces cluster naming writes each shown face reference, and the Photos/main-gallery inspector can scan or draw, save, select, name, rename, or unlabel individual face regions. The mutation and affected-identity prototype reconciliation run in a worker; a signal refreshes open Faces album, folder-review, identity, group, and Names views. Face model files are either in the managed runtime cache (normally `~/.local/share/ClusterLens/cache/face_model_assets` on Linux) or read directly from a user-selected external folder. Reusable managed download archives are kept beside them in `cache/face_model_downloads`. External files are never copied, moved, or deleted by ClusterLens.

Downloaded models are durable runtime data, not rebuildable caches. Face bundles are staged, checksummed, and published by atomic directory rename; an intent record outside the bundle directory allows startup to promote an interrupted install or restore a missing bundle from a verified local archive without networking. Clustering models share the same runtime cache in the app, worker, and downloader; startup repairs stale Hugging Face `refs/main` pointers to a complete local snapshot. The managed Hugging Face downloader and online loaders share one immutable revision map for MobileCLIP, DINO, DINOv2, CLIP, OpenCLIP and SigLIP; cache-only loading deliberately consumes the recovered local reference so offline recovery remains possible. Only the explicit model-cache deletion action removes these assets. Once this recovery completes, a `Startup` job evaluates the saved CPU/CUDA policy and local model availability without downloading or instantiating inference models. Its immutable report gates clustering and face actions and is the only runtime policy consumed by a clustering launch; launch never refreshes capabilities or constructs a provider on Qt. Settings invalidates the report, shows Checking, and starts a fresh coordinated probe after applying runtime/model changes. Actual model/session construction stays in cancellable face workers or the owned clustering child process, and explicit CUDA failures never silently retry on CPU.

`CacheMaintenanceService` owns all generated-storage boundaries. Its Storage summary reports rebuildable caches, the separately clearable Library catalog cache, thumbnails, generated face DB/ANN files, model caches, logs, temporary files, crash/support/benchmark reports, and installed model assets with the managed paths. A rebuildable SQLite cache is checkpointed, loses its WAL/SHM sidecars first, and removes its main file only at the explicit commit point; cancel or failure before that point leaves the main database independently usable. Large rebuildable directory caches are atomically detached to an exact sibling staging name before cancellable physical deletion. The live directory is recreated immediately; a crash, cancel, or post-detach permission error leaves a discoverable app-owned cleanup target, and Storage reports that Clear can safely retry it. Unsafe staging symlinks are never traversed. Production Settings routes its model inventory/install/delete, runtime probe, cache scan/clear, recovery history/restore, and Data Home AsyncJobs through the shared coordinator. Queued Settings work counts as busy and may be cancelled before its worker thread exists. Each role conservatively declares Data Home, model-cache, and active-source write ownership; one selected category is cleared at a time while tags, durable labels, operation-recovery journals, settings, and source folders remain protected by the service contract. This intentionally remains runtime-root storage only; no per-folder `.clusterlens` cache or legacy face catalog is used. Close-pending guards prevent startup/readiness workers from updating deleted Qt widgets.

Release evidence is separate from normal execution: `create_release_fixture.py` emits seeded synthetic PNGs plus a checksum manifest; `apps.shared.release_fixture` validates a declared fixture before release-gate benchmarking; trash recovery, frozen-launch, and native-display verifiers require disposable inputs and new report paths. They are validation tooling, not application data paths.

`AsyncJob` terminal events cross back to Qt through queued relays. Owners retain completed job/thread pairs for one event-loop turn, and close paths cancel, retain every still-running pair across repeated close attempts, then disconnect tracked UI observers only after drain. Disposal marks a job inert before signal disconnection; a queued relay rejects a disposed/deleted relay or job before touching public signals. Application-owned People workers are never detached to outlive a completed close. A deleted wrapper for an already-finished Gallery worker is treated as stopped rather than as a permanent close failure. `JobManager` and `WorkCoordinator` make already-queued signal delivery a no-op after their Qt owners are deleted. This prevents a thread-finished event from racing a queued completion or progress callback during shutdown.

All model download, indexing, cache maintenance, image decoding, folder discovery, and runtime resource probes run through background jobs. The UI thread only renders progress and applies completed results. Runtime policy tracks Torch and ONNX independently: built-in Torch face components follow the Torch device, while SCRFD/ArcFace and other ONNX components use the verified ONNX provider. The Faces status strip reports those actual stage devices. Support explicitly invalidates the cached result and runs its staged Torch CUDA, CUDA ONNX, and cuML-HDBSCAN checklist without opening user photos or model files, downloading packages/models, or changing the saved preference. Failed cuML imports are cached until that explicit rescan, avoiding repeated imports on every Auto-mode request. `scripts/run.sh` selects an already-installed dedicated CUDA source runtime and shares the normal per-user runtime-data/model paths with the CPU-compatible launcher; selecting CUDA is a provider/runtime decision, not a second copy of an ONNX model.

`JobManager` records each job's origin, foreground/background intent, progress, terminal outcome, cache/fallback status, and cancellation state. `JobPresentationController` is the sole writer to the shared footer progress area, giving active foreground work precedence while retaining passive work in the Jobs surface and its owning pane; it is stopped before the footer is deleted, so queued job updates become no-ops during close. Jobs history is one reusable modeless monitor with incremental 500-row updates, stable selection, an explicit compact cancel target and a fixed readable Details width. Production shutdown disconnects and closes that monitor before asynchronous worker draining can hide and retry the main-window close. `WorkCoordinator` owns admission and read/write resource locks. Its AsyncJob adapter registers one Jobs row and does not create a worker thread until ownership is granted. Startup/readiness, lazy People construction, Library, Tags, Names, SearchPane, shared Gallery actions, Sectioned layout preparation, Photo Inspector, production Settings, and the shell's discovery/preflight/tag/storage workers use this coordinator. Model-download and clustering QProcesses are also created only by coordinator callbacks; ownership covers the child-process lifetime. Jobs declare their initiating surface and conservative Data Home, source, model-cache, CPU/I/O and GPU needs. Queued work counts as active but has no thread/process, and cancellation before dispatch cannot start it later. Coordinated worker closures consume immutable values captured on Qt; SearchPane additionally records a route/root/model generation at submission and suppresses stale UI progress, success, and failure publication without hiding the durable terminal outcome in Jobs. Gallery, Sectioned Gallery and face-tile thumbnail decoders are the only direct UI producer exemptions: each is a bounded, viewport-demand-driven pool, cannot mutate durable state, and uses generation checks to discard stale publication. A static producer-inventory test rejects any new direct production start or live-widget access outside those pools. A clustering completion records its exact CPU fallback reason in Jobs. The Faces tab can additionally submit a current-folder, durable-unlabelled subset to the same clustering service solely to arrange a transient sectioned virtual tile grid; its request token is invalidated by filter/review/tab/name changes, it never writes labels or replaces Face Groups, and its outliers/drafts remain explicitly ungrouped. A Photos face-region edit that needs the global face service queues a callback behind the same cancellable Faces initialization job; it does not navigate to Faces or block Qt. Faces initialization has a generation token, so leaving Faces, replacing the window with the unsupported-resolution view, or closing the app cancels stale work and prevents a late completion from publishing widgets. During app close, Gallery work is cancelled and the window retries its close from the event loop until its workers drain; it does not wait on the UI thread. Gallery thumbnail workers are owned by their gallery and are demand-driven; an empty Faces pane does not create decoder threads until it has a visible tile to load. Background All Faces publication carries a generation token so it cannot replace a newer explicit search or cluster result.

The embedding service's execution policy is propagated into the clustering pipeline and every face-index service; lazy image-similarity services are rebuilt after an accepted runtime-policy change. The `ml` package exposes its public model classes lazily, so catalog/vector-store imports do not initialize Torch or ONNX. Standard presets and Faces grouping choose cosine K-means on verified CUDA, while a CPU runtime retains the established HDBSCAN Faces default. `VectorComputeService` owns vector execution: verified CUDA Torch runs semantic SVD/PCA, cosine K-means, sampled silhouette quality, chunked graph top-k, global image scoring, face search, identity propagation, and identity-comparison matrices; an import-verified RAPIDS cuML provider runs HDBSCAN. GPU calls are serialized per process and graph/K-means intermediates are row-chunked against a 256 MiB workspace ceiling so concurrently selected backends cannot create unbounded VRAM spikes. Auto HDBSCAN uses native CPU only with the exact provider failure recorded; an explicitly requested CUDA HDBSCAN operation fails with remediation rather than silently falling back. Other individual CUDA operation failures log and record their fallback reason before using native CPU libraries.

CPU vector fallbacks operate on contiguous float32 batches through NumPy/OpenBLAS, scikit-learn, and native HDBSCAN; cluster outlier/rerank post-processing is batched for cache locality. File HDBSCAN and face K-means parameters travel as backend-scoped request data through the production worker and service. Embedding, thumbnail, pixmap, face-tile, ANN, and cluster-result caches remain bounded or disk-backed. Cluster-result cache schema 4 includes backend options and the preparation/backend compute signature, preventing tuned, CPU, CUDA, or performance-profile outputs from reusing incompatible memberships. A reported CUDA fallback is not persisted under the GPU key. Control-heavy UI work, SQLite/filesystem boundaries, image decode, perceptual hashing, and ORB remain CPU-only.

Deep Name + Similar snapshots the complete initiating face scope in a worker, then uses the saved prototype followed by each newly found durable-unlabelled face as a temporary expansion frontier. It returns the deduplicated combined result without mutating storage. Faces and Names preselect only these still-unlabelled refs for an explicit metadata-aware apply; already-labelled other identities are shown but cannot expand the corpus or be overwritten. Full-scope scores use bounded rows through the shared CUDA/contiguous-CPU vector service, and all result publication/crop work stays model-backed and asynchronous.

## Library-first navigation and review queues

Desktop startup first creates `QApplication`, then a `QLocalServer` endpoint keyed by a hash of the canonical Data Home. A normal secondary launch hands an activation request to the owner and exits before `ProductionClusterApp` or its model/cache workers are built. `--new-instance` bypasses only this ownership guard. Within the primary shell, lightweight runtime migration and temporary cleanup unblock the People/Names shell; model-cache reconciliation and the CPU/CUDA readiness probe continue as separate cancellable Startup Jobs. Readiness, not initial pane construction, gates model-dependent actions.

The default persisted workspace is Library; a legacy saved Gallery choice migrates to Library at startup. Explicit legacy Gallery routes remain supported by mapping to Basic Clustering, where `SectionedGallery` retains the route's source, return destination, and per-photo inspector context. Basic mode displays active-root sections before any clustering run and reuses that surface for organized cluster sections. The comparison `GalleryPane` and cluster-detail splitter are advanced-only; Basic reveals details only after a successful cluster result, avoiding an empty side pane.

Library Search fetches catalog rows in cancellable 500-item pages. It publishes the first page to the viewport-driven `GalleryPane`, schedules further pages only while the query generation is current, and exposes the same footer control as **Stop loading**. Timeline deliberately retains its full scalar query. Count copy has one unit contract: **Loaded** is the unfiltered metadata snapshot, **Showing** is the currently published filtered or paged membership, and **Loading metadata X/Y photos** reports a known metadata phase. Photos, faces, groups and thumbnail decodes keep independent totals; `SectionedGallery` excludes label-cache reads from its thumbnail job and reports `Thumbnails ready X/Y`. Derived routes report only Showing because they do not own a comparable loaded snapshot. Its DateTimeOriginal-first policy is: manual correction, `exif_original`, other EXIF capture time, filename time, then modified time; provenance is kept as `exif_original` rather than flattened to generic EXIF. Catalog batches upsert durable rows and replace their FTS entries in one transaction, chunking deletes below SQLite parameter limits. Finite action surfaces across Detect, Library tools, Roots, Organize Advanced, Photo Inspector and Settings use the shared `ResponsiveFlowLayout`: controls retain natural widths and add vertical rows at the available content width. Long scalar labels use explicit elision with full tooltip content; editor/settings pages that can grow use vertical scroll boundaries with horizontal panning disabled. Duplicate selection actions remain hidden until a valid `DuplicateGroup` is selected. The selected group publishes to an embedded `SectionedGallery`: it is a model/view virtual thumbnail table, queues only its visible tiles, and retains the full-size photo-set handoff for inspection.

`DuplicateReviewService` accepts exact, near/similar, and burst kinds independently. Exact review hashes same-size candidates with SHA-256 and does not instantiate perceptual hashes or vectors. Similar review loads bounded pHash/dHash/wHash values and requires two backends to agree; stored vectors only reject a candidate when an available score is below the configured threshold. The visible Trash preview aggregates the current kind's non-keeper, non-keeper-anywhere paths, starts every checkbox unchecked, and dispatches only checked paths through the existing journaled, cancellable Trash action.

Names hover previews run as background People work admitted by the shared coordinator, with generation guards spanning queued and running states. The screen geometry chooses 9, 12, or 20 sample photos; the LRU cache key includes that layout. A bounded SQL query counts only durable visible labels on those sample paths, so the card can state co-occurring people without building a global relationship graph or reading unrelated source media.

Production child transport keeps QProcess construction, signals, and writes on Qt while moving proportional work outside it. Clustering and model-download requests are serialized in cancellable background jobs and streamed after process start. Protocol lines cap at 2 MiB, aggregate undecoded stdout at 4 MiB, retained diagnostic tails at 256 KiB, and managed file-backed results at 512 MiB. Both protocols share one validated progress contract: `-1` is the only unknown-total sentinel, 0 is determinate, phase-local completed/total pairs may derive a percentage, and processed/skipped/failed counts remain textual outcome detail. Progress retains only the newest update per 33 ms window and is flushed before exactly one guarded terminal event; late progress and competing terminal paths are discarded. Result jobs validate the managed handoff path, parse and normalize JSON, remove the file, and publish only for the current request generation. Diagnostic snapshots use one background writer that cannot recreate a removed runtime. Cancellation and close first request cooperative termination, then one child-owned timer escalates a still-running process to `kill()` after a bounded grace period. The timer checks exact QProcess identity, so it cannot kill a later replacement, and no path calls `waitForFinished`. Clustering publishes derived results only through the managed atomic handoff; model downloads retain reusable partial files and expose only checksum-verified promoted bundles, so forced escalation cannot expose a partial ready result.

The production UI treats filesystem, database and provider state as asynchronous snapshots. Library catalog schema initialization and Roots/album/count reads start lazily in an owned worker; the Qt side renders cached immutable navigation data. Startup validates a restored browse folder during maintenance, while saved roots and recent-folder labels use lexical normalization so an unavailable mount cannot block shell construction. Active-root discovery prepares its root-to-photo sections before publication. Face-pipeline changes rebuild and swap service sets in the People initialization worker; the service provider only selects an already-built cache entry on Qt. Confirmation dialogs remain on Qt, but their counts, purge plans and durable mutations are prepared and executed by owned workers.

Multi-file embedding indexes publish a checksum commit manifest only after the NumPy matrix, path map and optional FAISS artifact are durable. Interrupted or mixed generations have no valid manifest, are never reused, and are rebuilt deterministically.

Managed face-model replacement exposes durable checkpoints after the old bundle is staged and after the new bundle is published. Startup promotes only a checksum-verified candidate and removes a `.previous` directory only after the new target verifies. Photo-edit and exported metadata sidecars use atomic replacement and refuse to overwrite malformed existing data.

`docs/durable_operation_fault_matrix.json` is the machine-readable inventory for durable production operations. It maps each implementation to its before/commit/after boundaries, committed-subset meaning, cancellation behavior, idempotent recovery action, applicable fault classes, covered regression nodes and explicit gaps. `scripts/verify_durable_fault_matrix.py` executes that referenced Linux evidence with isolated settings/runtime state and process-session cleanup. Each of the 40 declared boundaries has a disposable worker that terminates itself with `SIGKILL` at the named production checkpoint; the parent records exact pre/crash/recovered state digests, requires two idempotent recovery attempts and rejects missing, duplicate or simulated kill evidence. A production-shell case also confirms startup reconciliation becomes visible in Safety & Recovery. A passing verifier does not substitute operation-level fault coverage for the complete boundary-by-fault cross-product or replace native Windows/macOS filesystem qualification; those remain separate gates.
