# Architecture

ClusterLens is a local PyQt desktop application. `apps.pyqt_production` builds the shell, owns QSettings/runtime services, and coordinates the Gallery, Clustering, lazy-loaded Faces, lazy-loaded Names, and Tags workspaces. Opening Names creates only the configured global face-index service on a worker, then loads durable labels; it does not require the Faces widget or face inference to be opened first.

Folder selection flows from `SourcePane` to the main window, gallery, and Faces folder review. The selected folder is the tree root; job status is separate from the persistent footer path chip.

Tags is a database-backed hub over `ImageTagService`'s `image_tags` SQLite table. Its `(tag_norm, image_path)` index supports deterministic pages of global/current-folder tag inventory and selected-tag photo paths without reading EXIF or source files. Gallery retains per-photo tag editing, including optional EXIF mirroring. Tags-only global rename/merge and delete change database rows only, by design. The Tags filter is the sole production source for tag-filtered cluster requests. Selected-cluster meaning generation is on demand: an `AsyncJob` creates local, no-download embedding/meaning services off the Qt thread, publishes only if the exact selected cluster remains current, and exposes cancellation/progress through `JobManager`; applying its labels is another background database-only mutation.

Clustering workers discover images, generate embeddings, cache results under the application runtime, and return compact result data to the UI thread. Gallery widgets use paged/model-backed presentation and bounded thumbnail caches. The thumbnail cache owns a SQLite access index beside its WebP files; opening it reconciles completed cache files, removes stale/unsafe rows, and recreates a corrupt index without touching source media. Multiple thumbnail services share a bounded process-local completed-recovery state only while the cache's WebP/index fingerprint matches, avoiding repeated recovery scans without persisting new state or bypassing recovery after a change.

Faces has two storage boundaries: per-folder review/index data and a global face database mapping face records to image paths. Faces always scans the folder selected in the shared folder pane; it has no competing folder override. Entering the Faces workspace asynchronously primes both boundaries from disk—global album plus selected-folder review—without indexing or rescanning. The primary task selector maps All Faces, Detect, and Find to retained internal pages; Review & Name and identity administration remain implemented but are deliberately hidden from that selector during the redesign. Find renders selected-face and query-photo actions in a responsive grid when the task pane is wide and stacks them when it is narrow; detailed guidance is available through hover and `i` help controls. Its older walkthrough and saved-search panel remains implemented but hidden. The active detector/embedder pipeline and review filters are selected in a modal editor.

All Faces uses model-backed group lists: Named Photos merges face tiles by their persisted person name, while Grouped Photos displays the raw clustering groups. Its sidebar maintains status internally for result publishing but renders only paged actions with hover and help affordances. The shared dense theme differentiates navigation tabs, subordinate result tabs, fieldset sections, primary actions, and secondary/configuration actions through explicit QSS selectors and `kind` properties. Face Groups keeps naming and photo viewing visible, moves less-frequent review/inspection work into Actions, and exposes cluster editing only through Advanced Actions. Background result filtering resolves saved metadata for every tile, so raw cluster titles list every current name in the cluster and naming in Detect, selected Grouped Photos tiles, grouped clusters, or another workspace is reflected in all views after the global album, folder review, identities, result groups, and Names refresh. Detected-face and Grouped Photos tiles use standard extended selection: Shift selects a range, Ctrl changes individual membership, and a right-click on an already selected tile preserves that selection. Raw cluster groups also support extended selection for batch naming. Single-face menus contain only single-face actions, while multi-face menus contain only batch-safe naming, clustering, and removal actions. Menus are shown asynchronously, so opening one does not nest a UI event loop. Find by Face embeds a supplied query photo; Find by Name + Similar uses the saved identity prototype embedding and therefore returns named and still-unlabeled similar faces.

Face labels are durable `(image_path, face_index) → person_name` rows in the global face SQLite database. Explicit user naming first merges the exact normalized face rectangles into MWG/XMP `mwg-rs:Regions`; a successful photo or sidecar write is required before its SQLite row is committed. JPEG embeds XMP and carries a ClusterLens EXIF UserComment mirror; non-JPEG formats and pre-existing XMP sidecars use `<photo>.xmp`. The XMP region list and custom mirror preserve unrelated metadata and every other face region. Re-index imports only an external region that matches an otherwise-unlabeled face; an existing database label wins on conflict. Automatic suggestions remain in `pending_face_labels` until review. A background global-album/Names refresh performs a one-time legacy recovery for earlier `manual_selected_faces` proposals; it promotes unconflicted rows, removes redundant duplicates, and leaves conflicts pending rather than replacing a durable assignment. The Names workspace reads only `face_labels`, uses a paged name list, and queries distinct image paths for the selected name on a worker thread. Its gallery is therefore a photo view of exact face mappings, not a similarity search. Hovering a name runs a separate cancellable worker query and builds at most a nine-photo contact sheet; a 24-entry in-memory LRU cache prevents repeated thumbnail work and stale results are discarded by generation. Its workspace-specific Rename and Unlabel actions first present the actual region names found in selected files, then mutate only the matching regions. Faces cluster naming writes each shown face reference, and the Photos/main-gallery inspector can scan or draw, save, select, name, rename, or unlabel individual face regions. The mutation and affected-identity prototype reconciliation run in a worker; a signal refreshes open Faces album, folder-review, identity, group, and Names views. Face model files are either in the managed runtime cache (normally `~/.local/share/ClusterLens/cache/face_model_assets` on Linux) or read directly from a user-selected external folder. Reusable managed download archives are kept beside them in `cache/face_model_downloads`. External files are never copied, moved, or deleted by ClusterLens.

Downloaded models are durable runtime data, not rebuildable caches. Face bundles are staged, checksummed, and published by atomic directory rename; an intent record outside the bundle directory allows startup to promote an interrupted install or restore a missing bundle from a verified local archive without networking. Clustering models share the same runtime cache in the app, worker, and downloader; startup repairs stale Hugging Face `refs/main` pointers to a complete local snapshot. Only the explicit model-cache deletion action removes these assets. Once this recovery completes, a `Startup` job evaluates the saved CPU/CUDA policy and local model availability without downloading or instantiating inference models. Its report gates clustering and face actions; Settings' resource rescan emits a completion signal that starts a fresh report without changing the saved preference.

`CacheMaintenanceService` owns all generated-storage boundaries. Its Storage summary reports rebuildable caches, thumbnails, generated face DB/ANN files, model caches, logs, temporary files, crash/support/benchmark reports, and installed model assets with the managed paths. A production Settings action invokes one selected category (or the explicit face/report groups) through an `AsyncJob`, measures freed bytes, and preserves tags, durable labels, operation-recovery journals, settings, and source folders. This intentionally remains runtime-root storage only; no per-folder `.clusterlens` cache or legacy face catalog is used. Close-pending guards prevent startup/readiness workers from updating deleted Qt widgets.

Release evidence is separate from normal execution: `create_release_fixture.py` emits seeded synthetic PNGs plus a checksum manifest; `apps.shared.release_fixture` validates a declared fixture before release-gate benchmarking; trash recovery, frozen-launch, and native-display verifiers require disposable inputs and new report paths. They are validation tooling, not application data paths.

All model download, indexing, cache maintenance, image decoding, and runtime resource probes run through background jobs. The UI thread only renders progress and applies completed results. Runtime policy tracks Torch and ONNX independently: built-in Torch face components follow the Torch device, while SCRFD/ArcFace and other ONNX components use the verified ONNX provider. The Faces status strip reports those actual stage devices, and Support can explicitly invalidate the cached capability result and rescan CPU, CUDA, and ONNX availability without changing the saved preference.

`JobManager` records each job's origin, foreground/background intent, progress, terminal outcome, and cancellation state. `JobPresentationController` is the sole writer to the shared footer progress area, giving active foreground work precedence while retaining passive work in the Jobs surface and its owning pane. Names, Faces, Photos/Inspector, Settings, storage maintenance, downloads, clustering, and startup recovery bind their workers to this contract. A Photos face-region edit that needs the global face service queues a callback behind the same cancellable Faces initialization job; it does not navigate to Faces or block Qt. Faces initialization has a generation token, so leaving Faces, replacing the window with the unsupported-resolution view, or closing the app cancels stale work and prevents a late completion from publishing widgets. Gallery thumbnail workers are owned by their gallery and are demand-driven; an empty Faces pane does not create decoder threads until it has a visible tile to load. Background All Faces publication carries a generation token so it cannot replace a newer explicit search or cluster result.

The embedding service's execution policy is propagated into the clustering pipeline and every face-index service; lazy image-similarity services are rebuilt after an accepted runtime-policy change. Standard presets and Faces grouping choose cosine K-means on verified CUDA, while a CPU runtime retains the established HDBSCAN Faces default. `VectorComputeService` owns vector execution: verified CUDA Torch runs semantic SVD/PCA, cosine K-means, sampled silhouette quality, chunked graph top-k, global image scoring, face search, identity propagation, and identity-comparison matrices; pinned RAPIDS cuML runs HDBSCAN. GPU calls are serialized per process and graph/K-means intermediates are row-chunked against a 256 MiB workspace ceiling so concurrently selected backends cannot create unbounded VRAM spikes. If an individual CUDA call fails, that operation logs and records its fallback reason before using native CPU libraries.

CPU vector fallbacks operate on contiguous float32 batches through NumPy/OpenBLAS, scikit-learn, and native HDBSCAN; cluster outlier/rerank post-processing is batched for cache locality. File HDBSCAN and face K-means parameters travel as backend-scoped request data through the production worker and service. Embedding, thumbnail, pixmap, face-tile, ANN, and cluster-result caches remain bounded or disk-backed. Cluster-result cache schema 4 includes backend options and the preparation/backend compute signature, preventing tuned, CPU, CUDA, or performance-profile outputs from reusing incompatible memberships. A reported CUDA fallback is not persisted under the GPU key. Control-heavy UI work, SQLite/filesystem boundaries, image decode, perceptual hashing, and ORB remain CPU-only.
