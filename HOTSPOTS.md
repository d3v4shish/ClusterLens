# Hotspots

- Timeline reads all matching catalog rows by design, but it reads only `image_path` and `captured_at` in a cancellable worker. The 1,200-row generated fixture measured a 1.072 ms median before the filename-date policy addition. Its remaining per-row ISO timestamp bucketing is already handled by CPython's C-backed `datetime.fromisoformat`; an attempted Python string fast path profiled slower and was not retained. Keep media metadata parsing, file stats, and thumbnail decode out of this path.

- Batch rename is deliberately latency-secondary to correctness: it preflights every source/target and rejects the entire preview on a collision, then performs individual same-directory atomic moves with a durable journal row before each change. Do not add automatic collision suffixes, cross-folder moves, or unjournaled background renames merely to shorten the operation; run it in its visible cancellable Job.

- Shared autocomplete choices are normalized and sorted once when an asynchronous service publishes a new list. The generated 10,000-name fixture measured a 2.879 ms median for population plus a contains filter after normalized-key reuse, down from 3.253 ms before eliminating duplicate case-fold scans. Do not query SQLite, rebuild the choice list, or create widgets on every keystroke; populate choices from cancellable workers and retain the normalized keys for filtering.

- Active-root union discovery is linear in the unique directories/files under the selected roots. The generated two-root, 80-photo fixture measured a 1.128 ms median on 2026-09-14; its profile was dominated by filesystem walks/stat calls rather than scope normalization. `PathScope` collapses nested selections before walking, and Gallery/Clustering invoke discovery only in cancellable workers. Do not turn a tree browse or scope-label update into a source walk, and do not replace path predicates with Python hydration of complete SQLite tables.

- Registered Library scans are source-read-only, cancellable background Jobs. The generated 240-JPEG/30-XMP fixture measured 47.388 ms median after bounded 48-asset SQLite upsert batches and XMP-sidecar revision checks, versus 121.486 ms before batching in the same fixture. The 2026-09-14 rerun measured 48.927 ms scan and 0.567 ms warm FTS-query medians; this is timing variance, not a new performance claim. Profile attributes remaining scan time to Pillow metadata reads, canonical path resolution, sidecar/filesystem stats, and five SQLite batches. Do not replace bounded batches with one uninterruptible whole-library transaction or move metadata reads onto Qt's UI thread. Retain the bounded LIKE fallback for SQLite builds without FTS5.
- Timeline deliberately has a different scale contract from Search: it reads every matching catalog row in a worker, but selects only indexed path/date scalars and fetches SQLite rows in 256-row cancellation batches. The generated 1,200-row source-free fixture measured a 1.087 ms median query/grouping baseline on 2026-09-14; profiling attributes the remaining cost to SQLite fetches and per-row ISO timestamp bucketing. Keep EXIF/XMP deserialization, file stats, and thumbnail decode out of this path. The nested `SectionedGallery` retains only model rows and a bounded visible thumbnail cache; do not replace it with one widget per month/photo.
- Library duplicate review reads only its requested persisted vectors in SQLite batches of at most 900 paths; it never loads an unrelated global vector corpus. The image-index read path and Library shell defer face-search, Torch, and ONNX imports until the user starts the corresponding People Cleanup, embedding, or visual-search action. Keep these boundaries lazy: the 2026-09-14 isolated startup-gate sample was 333 ms import, 406 ms window construction, 137.3 MiB RSS, and no eager heavy ML modules, against 1.0 s/1.5 s/256 MiB budgets.

- Gallery result routes are intentionally presentation-only: the routed path list and inspector context remain in memory, while folder discovery, thumbnail loading, analysis hand-off, and Faces review stay separate cancellable jobs. Do not turn Gallery route changes into a media scan or implicit face detection.
- cuML HDBSCAN availability is an import-level capability, not a package-name check. A failed provider import is cached until the user chooses Support → Rescan GPU Resources, preventing Auto mode from repeatedly paying import/error overhead. The staged worker first checks Torch CUDA, then CUDA ONNX, then cuML; it never opens media or models. The 2026-09-13 source-runtime benchmark had no cuML installed and correctly recorded a native CPU HDBSCAN fallback; no provider-import speed claim is made.
- Completion dialogs for long-running Faces export/index/label/import jobs were replaced by status-and-Jobs completion state. Modal confirmations and destructive-operation prompts remain explicit, but asynchronous completion must not start a nested event loop after its worker has already returned.

- Generated-storage scanning walks only known runtime-managed paths, but it can still be proportional to cache/model/report size. Settings runs summaries and all clears in `AsyncJob` workers with cancellation checks; do not add source-folder walks, EXIF reads, or synchronous size scans to the Storage tab. The packaged-launch smoke deliberately disables normal startup maintenance/model inventory so it measures only the frozen shell and Storage contract.
- Tags inventory pages group durable SQLite rows and are intentionally background jobs. cProfile attributed 0.552 of 0.842 seconds in the generated fixture to SQLite execution. The deterministic 75,000-row fixture measured 35.554 ms median for a 100-row global first page and 24.223 ms for a current-folder page; the indexed selected-tag path page measured 0.165 ms. The `(tag_norm, image_path)` index keeps selected-tag pagination cheap, while inventory grouping/source counts remain proportional to the in-scope tag rows. Later pages reuse the first page's total, avoiding an extra count query (33.333 vs 36.741 ms median for the matched global inventory page). Do not add EXIF/media probing to tag browsing; stale-entry reconciliation stays on explicit per-photo load/edit paths.
- On-demand cluster tag suggestions can load a local text/image model and embed up to the bounded cluster-meaning sample. This remains model/I/O-bound background work, with a no-download policy, a cancellable Job, and a selection-generation guard. It must not be moved into the clustering completion path or Qt thread.

- The seeded 10,000 × 32 HDBSCAN profile attributed 0.359 of a 0.401 second CPU call to native Borůvka/KD-tree fitting. The completed fixture measured 32.496 ms median with cuML on the RTX 4090 versus 390.741 ms native CPU, a 12.02× synthetic-workload throughput gain. cuML has a large install/package footprint and first-import/JIT cost, so it remains confined to the Linux CUDA artifact; CPU and unsupported systems retain native HDBSCAN.

- Per-face metadata writes are bounded per selected photo but are deliberately CPU/filesystem work: JPEG writes rebuild an EXIF mirror then atomically replace the XMP-injected file, while non-JPEG files atomically replace a small sidecar. The generated eight-region 1600 × 1200 JPEG baseline measured 11.037 ms median for merge plus readback. Large multi-photo changes run through existing background jobs; do not move image metadata writes to the UI thread or assume this synthetic local-I/O measurement covers network volumes.

- The 2026-09-13 seeded vector profile identified CPU MiniBatchKMeans as 0.756 of a 0.820 second profiled clustering call. The final fixed fixture measured 111.439 ms median with CUDA versus 424.828 ms for the CPU control. CUDA now covers PCA, K-means, sampled silhouette, graph top-k, and dense image/face/identity matrices; backend metrics record the actual device and any operation-level fallback. Treat this only as a synthetic vector result until a fixed photo fixture is measured.
- CUDA vector jobs are serialized per process and chunked to a 256 MiB intermediate workspace. This bounds VRAM and avoids selected clustering backends contending through simultaneous large allocations, at the cost of not overlapping two dense GPU backends in one worker.
- CPU fallback arrays are contiguous float32 and dense scoring/post-processing is batched through NumPy/OpenBLAS rather than Python-level per-record dot products. Runtime inspection on the validation host found OpenBLAS (16 threads), libjpeg-turbo, AVX2/FMA3, and available AVX-512 dispatch features. The optional FAISS package loaded its generic extension in the CUDA environment despite reporting optimized compile options; do not assume its AVX-specific modules are active.
- Image decode, embedding inference, ONNX model loading, face indexing, and filesystem discovery are potentially expensive and must remain off the UI thread.
- Face indexing is bounded by the batch-one SCRFD detector and filesystem/Pillow decode rather than the dynamic ArcFace crop batch. The generated 48-JPEG CPU-control scheduler fixture (four decode workers, two quality workers, 16-face embedding and write batches) measured a 100.786 ms median on 2026-09-14. Aggregate stage timings identify decode and SQLite writes as the substantial stages; their sums can exceed wall time because they overlap. Keep one detector lane, at most eight decoded full-resolution images in flight, bounded crop batches, and one transactional writer. Do not parallelize independent ONNX detector sessions on the same GPU without a VRAM/contention measurement.
- Foreground job presentation is deliberately coalesced on the UI thread; only the most recent active foreground operation owns the footer progress bar. Passive storage/audit scans remain inline to their owning Faces/Identity view. Faces and gallery tile decoders are started only when a tile is requested, avoiding idle QThread overhead for empty workspaces.
- Thumbnail and face-tile memory are bounded by model-owned caches; gallery/album views are paged to avoid creating widgets for all records. The transient Faces similarity arrangement uses a `QAbstractTableModel` grid with full-width headings, reuses the demand-driven face-crop queue, and sets only header-row geometry; do not replace it with one widget/layout per group or face.
- Folder Faces review resolves its metadata in at-most-500-image pages. Each page constrains its face-index and scan-state SQL reads to the page's candidate paths, then the UI appends model entries in short slices; decoded face crops remain limited to visible and prefetched rows. Candidate paths are canonically checked once at the outer page boundary and their keys flow to nested review/scan work; untrusted database rows retain canonical checking. The generated 1,001-row SQLite-only fixture measured 28.911 ms median for the first page and 76.459 ms for all `0, 500, 1000` pages after this reuse, but it intentionally excludes source discovery, media migration, crop decoding, thumbnails, and inference. The stable candidate-path snapshot is still proportional to the selected scope and is held only while its generation is active. Do not move discovery, SQLite page reads, final sorting, or crop decoding onto Qt's UI thread; use a fixed cold/warm photo-folder fixture before altering the 500-item bound.
- Names queries aggregate durable labels and resolve the selected name's distinct photo paths in worker threads. The names sidebar is paged; its gallery retains the standard bounded thumbnail loader rather than constructing one widget per photo. On the 2026-09-10 seeded 50,000-face assessment, the aggregate was 36.122 ms median and profiling attributed 39 of 40 ms to SQLite execution; the selected-name query was 1.119 ms median. Reassess the aggregate query with a larger fixed fixture before adding cache complexity or database indexes.
- Names photo-label actions resolve only face rows in explicitly selected photos and reconcile only the identities touched by that change. SQLite writes and prototype rebuilding remain on an `AsyncJob` worker; a very large selected-photo set can still require proportional database and embedding reads, so keep future bulk-operation progress/cancellation behavior covered by a fixed fixture before raising selection limits.
- Deep saved-name search intentionally visits every eligible indexed face and can grow a large frontier. It normalizes contiguous float32 embeddings once, scores 4,096-row batches through `VectorComputeService`, and checks cancellation between batches; CUDA uses the existing serialized matrix path and CPU uses NumPy/OpenBLAS. Keep result tiles virtualized and thumbnail decoding in workers. Metadata application is per-photo and cannot be atomic across files: cancellation retains only prior successful XMP/EXIF-plus-database commits, while conflicting labels are skipped.
- Model inventory only checks known managed paths and direct files in a user-selected model folder. It deliberately does not recursively scan arbitrary disks from the UI thread.
- Startup model recovery is local-only and runs before selectors are created. It hashes a retained face archive only when its verification sidecar is missing and a managed bundle needs restoration; normal launches do not rehash installed model payloads.
- CUDA availability depends on the installed Torch/ONNX Runtime provider and NVIDIA driver. The runtime badge reports general execution policy; the Faces status strip separately reports detector and embedder devices so CUDA Torch with CPU ONNX is not mislabeled as GPU face indexing. A verified CUDA runtime remains ready even when the badge tooltip also contains separate application-health notes. On Debian/Linux source installs, `scripts/setup_gpu_runtime.sh` creates the separate CUDA 12.1 runtime; after that `scripts/run.sh` prefers it without installation work and its verifier must confirm `CUDAExecutionProvider` before Face indexing is run with CUDA selected.
- A forced resource rescan invalidates the cached capability/provider result and can pay one-time CUDA initialization cost. On the 2026-09-12 RTX 4090 check, the first complete scan took 705.585 ms and two warm scans took 4.597 and 6.299 ms. It remains an explicit background job; do not move provider probing onto the Qt thread.
- Startup readiness intentionally repeats the local policy/model inspection only after startup recovery, settings changes, model installs, or an explicit resource rescan. It does not instantiate inference models or download files; it remains a cancellable `Startup` job because CUDA/provider probing can incur the same one-time initialization cost as a forced rescan. Thumbnail-index recovery similarly runs only when a cache index is opened and scans the bounded thumbnail cache directory, never a user photo folder.
- Independently owned gallery and preview `ThumbnailService` instances previously each reconciled the same cache when opened. On the generated 1,024-entry, four-service fixture this consumed 0.475 s in four recovery calls and produced a 200.411 ms median. A 32-entry process-local LRU now shares completed recovery by cache root only while the direct WebP and SQLite-index fingerprint still matches. The 2026-09-16 pass measured 41.152 ms across four services before and 19.107 ms after avoiding `resolve()` for normal direct WebP files; the first opener still resolves symlinks and database-originated paths, and an external-symlink regression proves they are rejected. Any changed fingerprint, cache clear, successful mutation, or corrupt-index reset invalidates/refreshes the shared state. The residual initial recovery remains linear in the bounded thumbnail cache; do not move it onto the Qt UI thread.
