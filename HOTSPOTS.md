# Hotspots

- **Full-resolution aligned crop and native-library footprint (UX-28/29, 2026-09-25)**: the corrected eight-photo 3840×2160 detector-path baseline showed that 32 five-landmark crops repeatedly converted the same full frame, costing 1,099.525 ms cold / 967.797 ms warm and 3.444 median CPU-seconds per full process. Each detector now owns one lazy full-frame array for one image pass; crop and thumbnail bytes remain identical while cold/warm crop medians fall to 339.003/268.321 ms, mixed completion falls from 1,095.233 to 334.598 ms and median CPU falls to 1.154 s. Residual profile cost is JPEG decode/color conversion; do not add an unbounded full-photo cache to remove it. The buffer is released after the detector batch: five traced cycles add only 6,188 retained Python bytes and have identical 676,040,704-byte current RSS. Absolute process peak remains high at 756–757 MB because importing the production face-search boundary loads native ML/runtime modules even though this fixture performs no inference. Mixed first content stayed about 12 ms; callback/input/pump p95 remained ≤0.031/0.022/1.792 ms with three fixed workers, a 32-item thumbnail cache and one crop buffer. Physical I/O is page-cache-dependent; logical reads are about 50 MB per process. Keep decode, conversion, crop quality and catalog I/O off Qt. GPU/model execution remains `NOT_USED`; real model/GPU memory belongs to UX-30.

- **Real detector/embedder loading remains unmeasured (UX-30, 2026-09-25)**: the opt-in harness and localhost download-fault matrix are implemented, but this host has no approved licensed face fixture or pinned model directory. The recorded preflight is exit 3 / `NOT_RUN`; it contains no inference timing or provider-memory sample. Do not use synthetic detector/embedder tests or the full-resolution crop benchmark as a model-throughput claim. Run the pinned manifest on qualified CPU and CUDA packages, then record cold/warm/recreated-service load, provider, RSS/GPU memory and OOM/fallback behavior before closing the hotspot.

- **Warm clustering worker resource retention (UX-15, 2026-09-25)**: two real Fast Preview ONNX CPU cycles retained about 610.0 MB RSS while the production child was deliberately idle/warm; model load was 0.666–0.712 s and four-image inference 0.009–0.013 s. Disabling warm mode removed each PID in 344.840–471.449 ms, and a later run started a distinct child with identical membership. The large idle footprint is mostly the Python/Torch/ONNX/native worker stack rather than the 3.7 MB model alone. Keep warm mode opt-in and truthful about memory. CUDA VRAM reservation/release remains unmeasured and must not be inferred from the CPU result.

- **Long-lived Qt test processes**: global `QApplication.setStyleSheet()` work is proportional to every live widget. The 2026-09-25 ordered production-support/theme fixture retained closed production windows until later deferred deletion, making individual theme tests take 15.86–65.68 s and the 78-test subset 163.28 s. Test teardown now closes top-level widgets, calls `deleteLater()`, flushes deferred-delete events, and collects Python cycles; the identical subset completed in 18.94 s. Keep this cleanup in any fixture that constructs production windows. This is test isolation evidence, not a runtime UI speed claim.

- **Close and child-process drain** is event-loop driven. A closing shell hides, retains every live job/thread pair across retries, and stays responsive while cooperative cancellation drains. Owned clustering/model children receive `terminate()` and only a still-running exact process is escalated by a 1.5-second timer; there are no Qt process waits or thread joins on the interactive close path. Do not clear retained references until the corresponding thread actually stops, and do not replace the identity guard with a global process lookup.

- **Release-host compute policy (2026-09-24)**: the deterministic 20,000 × 128 fixture measured 423.784 ms median for explicit CPU MiniBatch K-means and 113.040 ms for the selected CUDA path. The same host lacks `cuml`, so selected HDBSCAN correctly ran native CPU code in 361.994 ms with an explicit fallback reason rather than silently claiming GPU execution. Keep the runtime badge, Jobs detail, and benchmark report aligned with the effective provider; remeasure the CUDA package on its target driver/runtime before release.
