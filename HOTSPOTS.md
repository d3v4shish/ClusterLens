# Hotspots

- The seeded 10,000 × 32 HDBSCAN profile attributed 0.359 of a 0.401 second CPU call to native Borůvka/KD-tree fitting. The completed fixture measured 32.496 ms median with cuML on the RTX 4090 versus 390.741 ms native CPU, a 12.02× synthetic-workload throughput gain. cuML has a large install/package footprint and first-import/JIT cost, so it remains confined to the Linux CUDA artifact; CPU and unsupported systems retain native HDBSCAN.

- Per-face metadata writes are bounded per selected photo but are deliberately CPU/filesystem work: JPEG writes rebuild an EXIF mirror then atomically replace the XMP-injected file, while non-JPEG files atomically replace a small sidecar. The generated eight-region 1600 × 1200 JPEG baseline measured 11.037 ms median for merge plus readback. Large multi-photo changes run through existing background jobs; do not move image metadata writes to the UI thread or assume this synthetic local-I/O measurement covers network volumes.

- The 2026-09-13 seeded vector profile identified CPU MiniBatchKMeans as 0.756 of a 0.820 second profiled clustering call. The final fixed fixture measured 111.439 ms median with CUDA versus 424.828 ms for the CPU control. CUDA now covers PCA, K-means, sampled silhouette, graph top-k, and dense image/face/identity matrices; backend metrics record the actual device and any operation-level fallback. Treat this only as a synthetic vector result until a fixed photo fixture is measured.
- CUDA vector jobs are serialized per process and chunked to a 256 MiB intermediate workspace. This bounds VRAM and avoids selected clustering backends contending through simultaneous large allocations, at the cost of not overlapping two dense GPU backends in one worker.
- CPU fallback arrays are contiguous float32 and dense scoring/post-processing is batched through NumPy/OpenBLAS rather than Python-level per-record dot products. Runtime inspection on the validation host found OpenBLAS (16 threads), libjpeg-turbo, AVX2/FMA3, and available AVX-512 dispatch features. The optional FAISS package loaded its generic extension in the CUDA environment despite reporting optimized compile options; do not assume its AVX-specific modules are active.
- Image decode, embedding inference, ONNX model loading, face indexing, and filesystem discovery are potentially expensive and must remain off the UI thread.
- Foreground job presentation is deliberately coalesced on the UI thread; only the most recent active foreground operation owns the footer progress bar. Passive storage/audit scans remain inline to their owning Faces/Identity view. Faces and gallery tile decoders are started only when a tile is requested, avoiding idle QThread overhead for empty workspaces.
- Thumbnail and face-tile memory are bounded by model-owned caches; gallery/album views are paged to avoid creating widgets for all records.
- Names queries aggregate durable labels and resolve the selected name's distinct photo paths in worker threads. The names sidebar is paged; its gallery retains the standard bounded thumbnail loader rather than constructing one widget per photo. On the 2026-09-10 seeded 50,000-face assessment, the aggregate was 36.122 ms median and profiling attributed 39 of 40 ms to SQLite execution; the selected-name query was 1.119 ms median. Reassess the aggregate query with a larger fixed fixture before adding cache complexity or database indexes.
- Names photo-label actions resolve only face rows in explicitly selected photos and reconcile only the identities touched by that change. SQLite writes and prototype rebuilding remain on an `AsyncJob` worker; a very large selected-photo set can still require proportional database and embedding reads, so keep future bulk-operation progress/cancellation behavior covered by a fixed fixture before raising selection limits.
- Model inventory only checks known managed paths and direct files in a user-selected model folder. It deliberately does not recursively scan arbitrary disks from the UI thread.
- Startup model recovery is local-only and runs before selectors are created. It hashes a retained face archive only when its verification sidecar is missing and a managed bundle needs restoration; normal launches do not rehash installed model payloads.
- CUDA availability depends on the installed Torch/ONNX Runtime provider and NVIDIA driver. The runtime badge reports general execution policy; the Faces status strip separately reports detector and embedder devices so CUDA Torch with CPU ONNX is not mislabeled as GPU face indexing. A verified CUDA runtime remains ready even when the badge tooltip also contains separate application-health notes. On Debian/Linux source installs, `scripts/setup_gpu_runtime.sh` creates the separate CUDA 12.1 runtime and its verifier must confirm `CUDAExecutionProvider` before Face indexing is run with CUDA selected.
- A forced resource rescan invalidates the cached capability/provider result and can pay one-time CUDA initialization cost. On the 2026-09-12 RTX 4090 check, the first complete scan took 705.585 ms and two warm scans took 4.597 and 6.299 ms. It remains an explicit background job; do not move provider probing onto the Qt thread.
